TITLE: A Closer Look at Claude’s Mac “Apps”
OUTLET: MacStories

Yesterday, Anthropic announced a major new feature for artifacts, now available in beta for Mac and Windows: the ability for users to turn artifacts into “apps” they can install on their computers. From the company’s blog:
Starting today, you can use Claude artifacts to create, run, and share desktop apps. The “Install as app” feature is rolling out in beta in Claude for Mac and Windows.
When an artifact is installed as a Mac or Windows app, it gets its own icon and opens in its own window instead of inside Claude. You can share it with others, and it needs your permission before it can interact with your computer. You choose how much to allow.
Each app can use Claude and your connectors, and it updates automatically when the underlying artifact is edited. This simplifies the process for building and maintaining apps for both knowledge workers and developers. Requests the app makes to Claude count toward your plan’s usage limits.
If you’re an AppStories listener, you know that I’ve long thought it was only a matter of time until one of the big labs figured out how to turn their models’ frontier coding capabilities into a means to disrupt the App Store. This move feels like Anthropic’s first step in that direction.
Before I get into the technical details, let me say this upfront: if I were Apple, I’d be very concerned that Anthropic is now shipping a nicely packaged system for users to make whatever app they want and turn Apple’s ecosystem into Claude’s ecosystem of tools and mods on their computers.
Now, the way Anthropic made this happen can be debated, but I think the system is based on some clever engineering and savvy lock-in strategy. First, for these apps to work, you need the main Claude app to be installed and logged in with your account. These apps require the main Claude process to be running because every action they perform is actually handled by the Claude app behind the scenes, including permissions such as Full Disk Access. All apps made with Claude (either the ones you make, or the ones shared with you by other people) get installed at ~/Applications/Claude Apps, so they’re indexed by Spotlight and can be pinned to the macOS Dock. In fact, when you first create an app inside a Claude conversation (which can be a regular Claude session – you do not need to use Claude Code for these), there is a cute animation and install flow that puts an app directly in your Dock. It’s not too dissimilar from how the Shortcuts app can add individual shortcuts to your Mac’s Dock.
Crucially, these are not native apps created with Swift or SwiftUI: they’re HTML apps, wrapped inside an Electron shim, which is entirely managed by Claude’s Chromium process for Electron. It’s somewhat reminiscent of Raycast’s Glaze product, which uses Vite/React web apps, rendered inside Apple’s WKWebView, wrapped in a custom Swift shell. (Glaze also added the ability to integrate native Swift modules into their apps; I expect Anthropic to add this too.)

When the app was done, I asked Claude Code to explain how the other Claude built the app. Here is the Claude Code explanation of it all:
Storage Lens isn’t a traditional Mac app. Its 900 KB bundle holds no web code at all, just three pieces:
- A 51 KB Objective-C launcher, linked only against Cocoa and Foundation. It uses Electron’s “app shim” mechanism to find /Applications/Claude.app and load Claude’s copy of the Electron framework.
- An 80 KB notification helper built on UserNotifications. It won’t run unless it was launched by a signed Claude.app.
- An icon.
What looks like a standalone app with its own Dock icon is really a Claude process in disguise.
  The app itself is a single HTML file, written by hand with no third-party frameworks: no React, no Tailwind, no D3. It’s plain JavaScript, with one state object and render() functions that rebuild the page. Everything visual is hand-made:
- The capacity ring is an SVG drawn with stroke-dasharray tricks.
- The treemap uses a hand-written squarified layout.
- The app icon is drawn on a <canvas> each time the app launches.
- The Liquid Glass look comes entirely from CSS: backdrop-filter, light-dark(), and color-mix(in oklab).
- The sliding toolbar highlight uses an SVG distortion filter whose map is generated pixel by pixel, so it bends the background like a real lens.
  The interesting part is how a web page gets to touch the file system. Storage Lens calls window.claude.use('desktop'), an API that closely mirrors Electron’s own: childProcess.spawn, fs.readdir, shell.trashItem, Menu.setApplicationMenu, app.dock.setBadge. With that, it runs the same command-line tools a power user would:
- df -kP and diskutil for volumes
- du -k -x -d 2 for folder sizes
- mdfind with a kMDItemFSSize query for large files
  It reads their output line by line as they run and caches the results in localStorage. Nothing leaves the Mac.
That pretty much says it all. Liquid Glass is faked with CSS (incredible), everything is designed in HTML (not a surprise, given how much Claude loves pretty HTML artifacts), and all code routes through Electron via the main Claude app.

Anthropic has also published a support document that goes into more detail about what these apps can do, how permissions are handled, and what happens to an app you installed from someone else if the original creator stops sharing it. I found this part amusing:
If you lose access to an app, for example because its owner stops sharing it with you, the programs it started stop too. This can take up to about 20 minutes. It can take longer while Claude can’t check, such as when it’s offline, signed out, or using another organization.
So, unless you’re making your own apps, I wouldn’t build a serious workflow on top of an “app” created by somebody else, because they could stop sharing it at any moment and you’d lose access to it.
But then again: why be concerned if you can just prompt your way into a copy of it?
Many longtime macOS and native app purists will grimace at the mere thought of installing vibe-coded “apps” that are Electron wrappers bridging their commands to another app, and I get it. What Anthropic devised here is a hodgepodge of web technologies, disk permissions, and HTML UI that is the opposite of what native Apple app development should – at least in theory – still represent today.
At the same time, if I were Apple, I’d be concerned. Effectively, Anthropic shipped an app creation playground that only requires basic prompts to put together something that works. They did so by entirely bypassing the App Store or Apple’s notarization system for apps distributed outside the App Store, and by creating their own lock-in system around Claude’s identity and capabilities instead.
With Anthropic’s new artifacts-driven system, you’re making apps for your Mac, but, really, you’re making Claude apps for your Mac – which require your Claude account, can use your Claude connectors, and draw usage from your Claude account. Those apps just happen to live in your Dock and menu bar. But if they do what the user asked, who cares? And that’s what I think Apple should be concerned about: the evaporation of “care” for actual apps in the face of something that, ultimately, satisfies the user and doesn’t cost them anything extra.
You may argue: but surely these apps must be so limited, right?
Not quite. I haven’t pushed the limits of this system yet, but since Claude is just running shell commands and AppleScript under the hood, pretty much anything on macOS seems up for grabs.
Case in point: I had Claude reverse-engineer the Shortcuts database on the Mac to make a menu bar launcher for my shortcuts that displays their icons and organizes them by folder.
My idea was simple: since shortcuts can be run in the background on the Mac thanks to Apple’s shortcuts CLI, I figured Claude could make a nice menu bar launcher for them that also supported passing input from the clipboard. My prompt was:
make me an artifact that lets me run shortcuts from specific folders of the Shortcuts app from the menu bar. reverse engineer the Shortcuts database on this Mac so you can find its folders, shortcuts, and official shortcut icons and colors. make it beautiful and compliant with latest Apple HIG for Golden Gate. I want to select which folder I want to quickly access from settings, then the menu bar shows shortcuts from that folder. I click one, and it runs. There is an optional mode to run a shortcut with the contents of system clipboard as input. You can use the native shortcuts CLI for this.
Interestingly, Claude tried to request permission to reverse-engineer the Shortcuts database on my MacBook Pro, but it didn’t work even after I granted permission:
Instead, Claude used MacRemote – my upcoming tool to connect a Mac’s tools and filesystem to any AI agent, soon to be open sourced – to ping my Mac Studio and figure out the Shortcuts.sqlite database there. A few minutes later, I had a working version of the app that let me pick a folder for quick access and run my shortcuts from the menu bar. Through a mix of osascript and Full Disk Access, Claude put together a wrapper that looks nice and took just a few messages in a chat.
