TITLE: Unsupported Google tag installs get the Tag Manager upgrade in January 2027
OUTLET: PPC Land

Google today published a release note that turns the merger of the Google tag and Google Tag Manager, first announced in May, into a documented change. Under the heading "Google tag and Google Tag Manager unification," the note states that "each Google tag becomes a Tag Manager container," that Tag Manager's permission settings will now govern access to data in Tag Assistant, and that installations Google classes as unsupported will receive the upgrade in January 2027.
In Short
Google's Tag Manager release notes now state that each Google tag becomes a Tag Manager container, giving sites that only use the Google tag access to Tag Manager's tagging interface, debugging and version control. Anyone who installed Google Ads or Google Analytics with the plain Google tag is affected, because access to Tag Assistant data now runs through container permissions and new installation snippets no longer carry the gtag config command. Google says the tags will behave the same way on the page, but installations it considers unsupported get the upgrade in January 2027, and Google advises adjusting them before then.
What Google's release note sets out
The entry sits at the top of "Release notes for Google Tag Manager" in the Tag Manager Help Center and runs to five short paragraphs. Read in order, it describes the change in seven parts.
- The conversion. "We're bringing all the capabilities of Google Tag Manager to the Google tag. With these upgrades, each Google tag becomes a Tag Manager container," according to Google.
- What Google tag-only sites gain. "Websites that only use Google tag will have the ability to use Tag Manager's interface-driven tagging features, debugging, and version control."
- What stays the same. "This upgrade won't change the in-page behavior of the Google tags. Rather, advertisers who use Google tag will gain the option to use Google Tag Manager features."
- Destinations. "Each Google destination will have its own tag, preserving your existing setup and triggers for automation events."
- Snippets and initialization. "With this change, all new deployment snippets will be the same. Additionally, they won't have the gtag config command." Google recommends configuring initialization "using the standard Google Tag Manager initialization triggers" and adds: "The Initialization trigger can also configure the tag to wait for the config command if you want to preserve legacy setup."
- Permissions. "Google Tag Manager permission settings will now apply across the board, meaning access to data in Tag Assistant will be managed through the container permissions you use in Google Tag Manager today."
- Unsupported installations. "If you have an unsupported installation, you'll receive the upgrade in January 2027, and are advised to adjust your setup before then."
The note gives no start date for supported installations and no date by which the conversion will be finished. Its tense, though, is the present: the tag "becomes" a container. That matches what practitioners have been seeing in their accounts. A day earlier, Julius Fedorovicius, founder of analyticsmania.com, showed that the "Configure tag settings" link in a Google Analytics web data stream now opens a Tag Manager container created for that stream, identified by a GTM- ID and carrying a banner announcing the upgrade.
What changed from the August wording
Google first set out the plan on May 20, 2026, in a Help Center page titled "Updates to Google tag and Google Tag Manager" that PPC Land examined at the end of May. That page now carries the date August 20, 2026; when it reappeared, PPC Land found the May text had been re-dated rather than expanded. Much of today's release note repeats that page nearly word for word. Not all of it.
Three differences stand out. The first is tense: a future upgrade has become a present one. The second is the permissions paragraph, which did not appear in the unification section of the Help Center page. The third is a date. For six months, Google described the merger without saying when anything would happen to installations outside its supported patterns. Now there is a month.
The January 2027 date and what "unsupported" means
The release note does not define an unsupported installation in its own text. The phrase links to a separate Help Center page, "Set up your Google tag installation correctly for gtag.js." That page deals with sites that load a Google Analytics (G-), Google Ads (AW-) or Floodlight (DC-) ID through the gtm.js snippet, which is the code meant for Tag Manager containers, and then rely on gtag('config') commands. "This is an unsupported implementation, and sites using them may experience unexpected changes to their tag behavior," according to Google. The supported route for gtag('config') commands, the page says, is the standard Google tag snippet loaded from googletagmanager.com/gtag/js with the tag's ID.
The release notes apply the same label to the mirror image. A July 9, 2026 entry dealt with "containers loaded using unsupported paths such as /gtag/js or /gtag/destination," which until then had been degraded to a restricted state. Google replaced the path-based rule with one based on the ID. "Moving forward, the ID used to load the container will control this behavior, regardless of the path used," the note reads. "Containers loaded with a GTM-XXXX ID won't be restricted, while product-specific ID types like G-XXXX or AW-XXXX will only permit tags and variables provided by Google." PPC Land reported at the time that the earlier rule had locked down some containers that should not have been restricted.
Then came October 8. In a note titled "Standardizing gtag('config') command behavior for Google Tag Manager," Google said that "all Google Tag Manager (gtm.js) container snippets will initialize on container load, regardless of any gtag('config') commands." Config commands would now "surface in the dataLayer as visible gtag.config events," and Google warned that containers using wildcard custom event triggers might see those tags fire. That change, which PPC Land covered the following day, pushed sites that mix gtm.js snippets with gtag('config') onto gtag.js. The gtag.js setup page still opens with a notice that gtm.js snippets "will soon be updated to no longer recognize or wait for any gtag('config') commands," wording that predates the October entry.
January 2027 is therefore the date on which the unification reaches the installations that Google has spent the second half of 2026 steering back onto its documented snippets. What happens to an installation that has not been adjusted by then is not spelled out. The release note says only that it will "receive the upgrade."
Four release notes that cleared the path
The unification did not arrive in one step. Google's release notes record a sequence that began in 2025, with Tag Manager made to depend more heavily on the Google tag, and is now ending with the Google tag absorbed into Tag Manager.
The two ends of that table point in opposite directions. In March 2025, Google wrote: "Starting April 10, 2025 containers with Google Ads and Floodlight tags will automatically load a Google tag first, before sending events." Nineteen months later, the October 12 note described that extra layer as a problem. "Previously, Google Tag Manager loaded extra javascript (gtag.js) to send data to a Google destination, which could cause latency in measurement transmission," according to Google. "The Google tag that was loaded also had its own settings and permissions, which sometimes made troubleshooting difficult, and could result in fragmented diagnostics."
Today's note completes the reversal. Rather than a container loading a Google tag, each Google tag becomes a container. The September entry is a small piece of the same picture: sites that only used the Google tag now inherit Tag Manager's version control, and with it a submit page on which, according to Google, "The AI summarizes the changes in the workspace and automatically proposes a Version Name and Version Description."
Permissions move into the container
The permissions paragraph carries the most practical weight. Tag Assistant is the tool Google provides for previewing and debugging tags on a site. Until now, a Google tag had its own settings and its own permissions, separate from any Tag Manager container on the same site - the separation Google's October note blamed for difficult troubleshooting. Under today's note, access to Tag Assistant data follows the container permissions already used in Tag Manager.
In practice, whoever administers users on the container now decides who can see that data. In organizations where an analytics team runs Tag Manager while a media agency manages Google Ads measurement through Google tag settings, those two lines of control now meet in one place. Google's note does not say which Tag Manager account holds a container created from a Google tag, or which users are added to it at conversion.
Practitioners have noticed. "The quiet part here is governance: every upgraded stream gets its own container with its own users and publish rights," Björn Thomsen, a B2B head of marketing, wrote in a comment on LinkedIn. That description of per-stream containers is his, not Google's, though it matches the container created for a single Google Analytics stream that Fedorovicius documented on November 16.
How Simo Ahava read it
The release note drew an early response from Simo Ahava, co-founder of Simmer and a partner at 8-bit-sheep, who posted about it on LinkedIn today. "Google Tags are now Google Tag Manager containers," he wrote. "Instead of managing Google Tags via their own settings interface, you will now control them with the GTM UI. They will retain all Google Tag capabilities but will now benefit from a more unified approach to tagging under Google."
He did not pretend the product lines had been easy to follow. "Once the migration is complete, hopefully some of the confusion introduced by the GTM upgrade will be dispelled. However, Google Tag vs. Google Tag Manager is still confusing even for experts and power users. Maybe with this consolidation it will be easier to grok each system's role in a marketing setup," according to the post.
On data, Ahava was direct. "Again, importantly, on-page behavior doesn't change. This doesn't introduce additional data collection or processing beyond what the tags have already done and been capable of." Google's note limits itself to in-page behavior and does not address data collection in those words. What the tags were already capable of had itself widened earlier in the year: a February 4, 2026 release note said Google Ads would measure "by automatically collecting a broader range of event data from their websites," and that advertisers "may notice additional network requests to Google domains."
Ahava's reading also goes a step further than Google's text on the interface. The release note speaks of advertisers gaining "the option" to use Tag Manager features. Replying to a commenter, Ahava wrote that "Google Tag will no longer have its own setup UI, but instead will be configured and maintained in the shape and form of a GTM container." The note itself does not say the Google tag's settings screen is being retired, although the Analytics link that now opens a container points in that direction.
The comments under the post were mixed. "How can they make something that should be so simple and transparent this complicated?" asked Brais Calvo Vázquez, an analytics developer. Alessandro Colarossi, director of account performance at SearchKings, wrote: "How does it become a container? weird.." John Barnes, an analytics specialist, asked: "what does this actually change in context of the recent changes we've already seen in the UI and the new install script?" He also singled out the line on unsupported installations.
