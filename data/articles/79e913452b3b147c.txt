TITLE: Google shrinks idle tools in Gemini agents to about 26 tokens each
OUTLET: PPC Land

Google today put Tool Retrieval into preview in the Gemini API, a mode that lets an AI agent keep most of its tools out of each prompt and fetch a tool's full definition only when a task calls for it. Announced in a three-minute post by Lucia Loher, a product manager on the Gemini API, and Nora Kassner, a research scientist at Google DeepMind, the feature works only in the Interactions API and on Gemini 3.6 and later models, carries no separate fee, and follows near-identical designs from Anthropic in November 2025 and OpenAI in March 2026, down to the name of the flag that switches it on.
In Short
Google has added an option to its Gemini developer platform that lets AI agents hooked up to dozens or hundreds of tools carry only a one-line note about each tool, pulling in the full instructions for a tool only when a job needs it. That matters to anyone building agents on top of advertising platforms' AI connectors, where every connected tool's full definition has until now been resent, and billed, with every request. Google gives no figure for the savings, and its own documentation shows that each lookup adds a billed pass of its own, so the effect on cost depends on how many tools an agent has and how often it goes looking for one.
One new tool and a flag
"Today we're launching Tool Retrieval in the Gemini API, available in preview in the Interactions API," the post begins. Published on Google's blog under the Developer tools and AI tags, it runs to two code samples and a pricing section. There is no benchmark, no customer name and no general availability date.
The problem it addresses is stated in a single paragraph. "When an agent connects to dozens or even hundreds of tools, sending every full parameter schema on every request adds up fast," according to Google. "It inflates input token counts, adds latency, and lowers tool-selection accuracy as the candidate list grows." Google attaches no number to any of those three effects.
Some background explains why the schemas pile up. In conventional tool calling, a developer declares every function an agent is allowed to use, and each declaration includes a parameter schema: a structured list of the function's arguments, their types and which of them are required. The whole set travels with each request, so the model can read it before deciding what to call. Every schema consumes tokens, the units in which model providers meter and bill text, and every schema takes room in the model's context window, whether the task at hand needs that tool or not.
Tool Retrieval splits each declaration in two. The name and a short description stay in the prompt. The parameter schema stays out until the model asks for it.
How it works, according to Google
According to the post and the documentation it links to, server-side Tool Retrieval runs in six steps.
- The developer adds a tool_search tool to the tools array of an Interactions API request. Exactly one tool_search tool is allowed per request, according to the documentation, which also states that the feature is in preview and requires the v1beta version of the API.
- The developer sets defer_loading: true on each tool to be held back. This works on individual function declarations and on entire remote MCP servers, the connectors through which software vendors publish tools for AI agents. Google's sample code defers "50+ other deferred functions" and carries the comment "leave frequent tools undeferred"; the post says the most-used tools can stay loaded up front while "the long tail" is deferred.
- The model sees a compact listing. It "still sees the name and description of every deferred tool, so it knows what's available, but the parameter schemas stay out of context," according to the post. The documentation is more specific: each deferred tool adds one line containing its name and an optional short_description field, or the first sentence of its full description if no short description is set.
- The model requests a tool by name. It emits a tool_search_call step whose arguments, in Google's example, are a list of function names.
- The API loads the schema. A tool_search_result step returns the full declaration, parameters included.
- The model calls the function. A normal function_call step follows, the developer's own code executes it and returns a function_result. "From here it's normal function calling," according to Google.
Steps four to six happen, in Google's words, "all inside the same request." Google's example is a customer-service agent asked to refund 40 dollars on a damaged order, A-1042. The model searches for a function called issue_refund, receives its schema, which takes an order_id string and an amount number, and emits a call with {"order_id": "A-1042", "amount": 40}. All three steps are recorded in interaction.steps, which the post describes as a way "to inspect which tools the model considered when debugging tool names or descriptions."
"There's no index to build or host," according to Google. "Gemini runs the search on the server, so the only changes to your code are the new tool and a flag on the tools you want to defer."
What the post calls a search is, in its own example, a selection: the model names the function it wants from a list it already holds. Neither the post nor the documentation explains how the server matches tools beyond that.
Remote MCP servers and the cached prefix
Two further claims in the post bear directly on agents that sit on top of third-party platforms.
The first concerns servers built on the Model Context Protocol. "Tool Retrieval also works with remote MCP servers in the Gemini API," the post says. Setting defer_loading: true on an mcp_server tool means "every tool that server exposes is loaded on demand, so you can connect a large server without listing its tools one by one." The mcp_server tool object itself is recent: Google added remote MCP server support to the Interactions API on July 7, 2026, alongside background execution for long-running agent tasks.
The second concerns caching. Model providers charge less for input that repeats exactly from one request to the next, but only while the opening stretch of the prompt, the prefix, stays unchanged. A schema inserted near the top would break that. "Deferred schemas stay out of the start of the prompt, and the schemas the model loads are added later in the conversation, so the cached prefix stays the same from turn to turn," according to Google.
The point is not academic. When a16z analysed agent traffic on the OpenRouter network in August, it found that more than 85% of agentic token burn sat in the cached prompt, and that agents used close to five times as many tokens as human users. For Gemini 4 Argon, Google priced cached input at 95% off the standard input rate. A feature that disturbed the cache would cost more than it saved; Google's claim is that this one does not.
Client-side retrieval for companies with their own registry
A second mode hands the search to the developer. Companies that run their own tool registry, embedding index or per-user permission filter, the three cases the post names, can declare the tool_search tool with "execution": "client" and define their own search parameters. In Google's sample, the tool is named search_tools and takes a single query string.
The model then emits an ordinary function call to that search tool. The application runs the lookup against its own systems and returns matching function declarations in a function_result, in a follow-up request that references the earlier one through previous_interaction_id. According to Google, this costs one additional round trip per search, because the application rather than Google runs the lookup.
The trade-off buys flexibility. "Tools do not need to be declared upfront," according to the post, so an agent can be handed new tools mid-conversation, for instance "when a user connects an integration." With a per-user permission filter, the application rather than Google decides which tools a given user's agent can reach. Server-side and client-side retrieval cannot be mixed in a single request, according to the documentation.
What it costs
"Tool Retrieval has no separate charge," according to Google. "Input and output tokens are billed at the standard rates for the model you call." That does not make it free. Read together, the post and the documentation set out how the bill is built.
The last two rows matter most, and only one of them appears in the post. The blog describes the search, the schema load and the function call as happening "inside that single API call." The documentation confirms that they share one request, and adds that inside it the API runs a second model call over the whole context to process the search. For a long conversation with a large context, that pass is not small.
Google's own conclusion is hedged. Savings arrive when the schemas never loaded outweigh the ones that are, "which is the usual case for large libraries," according to the post, which closes its pricing section by telling developers to measure the effect "against your own traffic."
How much does the listing itself cost? At about 26 tokens a line, a library of 100 deferred tools adds roughly 2,600 input tokens to every request, by PPC Land's calculation. At Gemini 4 Hydrogen's published rate of $1.50 per million input tokens, that is about $0.004 per request, or about $3.90 per thousand requests, before any schema is loaded, any search pass is run or any output is generated (PPC Land calculation). What the same 100 tools would cost with full schemas cannot be calculated from Google's material, because neither the post nor the documentation gives an average schema size.
Which models qualify, and a discrepancy
"Tool Retrieval works with Gemini 3.6 and later models, including all Gemini 4 models, in the Interactions API," according to the post. The documentation narrows that statement. It lists four supported model codes and says requests that set defer_loading on any other model return a 400 error. The older generateContent method does not support the feature at all.
Gemini 4 Carbon, which Google made generally available on November 10 at the same introductory price as Argon, appears nowhere on the documentation page. Neither does Gemini 3.7 Flash, one of the models Google listed for agentic video understanding on September 1. Whether the post or the documentation is out of date, Google does not say. Prices for Gemini 3.6 Flash come from its July 21 launch; the code samples in today's post call gemini-4-hydrogen.
The rules in the documentation
Beyond pricing and models, the documentation sets out several constraints that the post does not mention. In paraphrase:
- Nothing unloads. Once the model has loaded a tool's schema, there is no way to remove it from the conversation.
- The full tool list travels every time. The API does not carry tool declarations from one request to the next, even when previous_interaction_id is passed, so the complete tools array has to be sent with every request in a conversation.
- Named tools cannot be deferred safely. If a tool's name appears in the system instructions or in another tool's output, the documentation says it should not be deferred. Otherwise the model may call it without searching first, and the next request fails with an error beginning Server side tool call context must be circulated.
- A miss is silent. A query that matches no deferred tool produces a text response rather than a structured retrieval error, and the documentation warns against relying on a tool_search_result step to detect a miss.
- One mode per request. Server-side and client-side retrieval are mutually exclusive within a request.
- Subject to change. The API surface may change before general availability.
