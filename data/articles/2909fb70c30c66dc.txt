TITLE: Apple's Safari preview stops losing analytics beacons when pages close
OUTLET: PPC Land

Apple's WebKit team on November 18, 2026 published release notes for Safari Technology Preview 257, an experimental build of Safari for macOS Golden Gate and macOS Tahoe that lists 201 changes to the browser engine. Ten are new features. The remaining 191 are fixes, and a small group of them sits in the plumbing that analytics scripts, ad tags and privacy extensions rely on: requests sent as a page closes, the timing entries a page records for its iframes, and the rules extensions use to remove parameters from URLs.
The most direct of them for measurement is a single line under Networking. "Fixed beacons sent from pagehide being lost when a page is closed and its process shuts down," according to the notes.
In Short
Apple released a test version of Safari on November 18 with 201 changes, including a fix for data that websites try to send at the moment a page is closed, which was being lost. That matters to anyone measuring websites in Safari, because analytics and ad scripts often send their final report as a visitor leaves, and to makers of privacy extensions that remove tracking parameters from links. The notes do not say when any of these changes will reach the Safari that people use every day, so for now they show what Apple's engine team has fixed, not what has shipped.
A test browser with a long version history
Safari Technology Preview is the build in which Apple ships WebKit engine work before it reaches the regular browser. The notes link its name to WebKit's original post introducing the program, and when PPC Land covered Safari Technology Preview 192 in April 2024, it described the release as a glimpse of where Apple's production browser was heading and noted that it installs alongside regular Safari. Sixty-five numbered releases separate that build from this one (PPC Land calculation).
Release 257 is signed by Saron Yitbarek. According to the notes, it includes WebKit changes between 324654@main and 326096@main, and that range links to a comparison of two commits in WebKit's public GitHub repository. The span covers 1,442 commit numbers (PPC Land calculation). Each of the 201 entries carries its own commit identifier, linked to commits.webkit.org, and a second reference number in parentheses that the notes do not explain.
Most of the release is unglamorous. CSS alone accounts for 51 fixes, many of them about flexbox and grid sizing. Three separate entries correct flex layouts that ended "up to 1/64 of a pixel short of the end edge" of their containers. Web Extensions is the second-largest category, with 31 entries, followed by Web API with 29.
How the release is distributed
According to the notes, the build reaches developers in the following way:
- The release is available for two operating systems: macOS Golden Gate and macOS Tahoe. No iPhone, iPad or Vision Pro build is mentioned.
- Machines that already have Safari Technology Preview installed receive the update through System Settings, under General, then Software Update.
- New installations start from Apple's Safari resources page for developers, which the notes link from the words "available for download."
- Each entry links to its commit on commits.webkit.org, so a developer can read the code change behind any line in the notes.
The last request before a page closes
The beacon fix is short, and its wording is precise about the conditions. Two things had to happen together for the data to disappear: the page was closed, and the process running it shut down. In that case, beacons sent from the pagehide event were lost.
Pagehide is the event a browser fires when it leaves a page, including when a tab is closed. A beacon is a small request designed to leave the browser at exactly that moment, without holding up navigation. Analytics libraries and the tracking pixel calls that ad platforms use for measurement often rely on that window to send the last piece of a session: engagement time, final scroll depth, an exit event. If the browser tears down the process before those requests go out, the session ends without them, and the report arrives incomplete.
How many sessions ended without their final beacon? The notes do not say. They give no share of beacons lost, no indication of how long the bug existed, and no statement on whether shipping versions of Safari behave the same way. They also do not name the specific web interface involved. What they establish is narrower: in Technology Preview 257, WebKit treats the loss as a bug and says it has been fixed.
For marketers, the timing is notable. Most of the Safari stories that have reached advertisers this year have been about Apple choosing to limit measurement, through Intelligent Tracking Prevention, the Safari 27 block on The Trade Desk's adsrvr.org domain, or the block on identity firms that turn email addresses into tracking IDs. The pagehide fix belongs to a different category: data that a page tried to send and that the browser dropped by accident.
Every iframe navigation, now on the record
A second measurement change sits under Web API. "Fixed an issue where only the first navigation of an iframe was reported in the parent document's Resource Timing entries. Every navigation initiated by the parent document is now reported," according to the notes.
Resource Timing is the browser interface that records how long each resource on a page took to load. Performance monitoring tools read it to find slow third parties, and iframes are where much of that third-party content lives. When PPC Land reported in September that Chrome had put publishers' ad loads on public record with four new metrics, the coverage noted that most ads run in cross-origin iframes, which is why the measurement has to happen inside the browser.
Under the old behavior in WebKit, a parent page that pointed an iframe at a new address would see only the first load in its timing data. The fix covers navigations "initiated by the parent document." Navigations an iframe starts on its own, such as a redirect from inside the frame, fall outside that wording, and the notes do not address them.
Two smaller entries touch the same area. A fix to Cache's match() and matchAll() means they now "queue Reporting API Cross-Origin-Resource-Policy violation reports when a cross-origin opaque response is blocked." And ReportingObserver reports and their bodies are now "plain objects, so they can be structured-cloned and posted," with their toJSON() methods removed. A separate fix stops ReportingObserver from invoking its callback with no reports after takeRecords() was called.
Link headers and preconnects from third parties
One Networking entry changes how Safari treats hints sent by servers. "Fixed Link response headers on subresources (such as CSS, scripts, and fonts) incorrectly triggering rel=preload and rel=preconnect. Only the main resource now does," according to the notes.
Preload and preconnect tell a browser to fetch a file early or to open a connection to a server before it is needed. In the old behavior, a script or stylesheet served by a third party could carry such a hint in its HTTP headers, and WebKit would act on it. In Technology Preview 257, only the hints on the page's own main document count. The notes describe the earlier behavior as incorrect, so any vendor that benefited from it in Safari was relying on a bug.
Two further entries are relevant to the scripts that tag managers and analytics libraries schedule. requestIdleCallback no longer drops its timeout "when the callback was already in the list of runnable idle callbacks." And window.print() no longer waits for active XMLHttpRequest requests, "such as long-polling," to finish before showing the print dialog.
Extensions and the rules that rewrite URLs
The Web Extensions section matters to a different audience: the developers of content blockers and privacy tools, and the advertisers whose links pass through them.
Safari extensions can declare rules through an interface called declarativeNetRequest, which the browser applies to network requests on the extension's behalf. Those rules are bounded by the browser extension permissions each extension declares in its manifest. One of the actions a rule can take is a redirect that rewrites the URL, and one form of rewrite, queryTransform.removeParams, deletes named query parameters from it.
Technology Preview 257 fixes how several of those rules combine. According to the notes, it "Fixed declarativeNetRequest redirect rules of equal priority from the same extension that only remove query parameters with queryTransform.removeParams so they all apply instead of only the first."
Read literally, an extension that defined one rule per parameter at the same priority would, before this build, have stripped only one of them from a matching URL. In 257, all of them apply. The notes name no parameters and no extensions. For paid search, the parameters most often discussed in this context are click identifiers such as the GCLID that Google Ads appends to each ad click, which is how conversions are tied back to a click. Safari's own protections already strip it in some modes: PPC Land's testing of the iOS 26 beta in September 2025 found gclid intact in regular browsing but removed when protection for all browsing was switched on manually and for links opened from Mail and Messages, and an April 2026 estimate put the stripping at roughly 20% of sessions under Private Browsing's default protection. Extensions are a separate layer on top of that, and this fix makes their parameter rules behave as written.
Three other declarativeNetRequest entries point the same way:
- modifyHeaders rules no longer reject custom header names.
- The quota check for updateDynamicRules and updateSessionRules no longer counts existing rules twice, so extensions are no longer refused before reaching their actual limit.
- declarativeNetRequest.ResourceType is now one of the enum types added to the browser.* namespaces, alongside cookies.SameSiteStatus, extension.ViewType and menus.ContextType.
Other extension entries tighten security. tabs.update() no longer allows extensions "to navigate a tab to javascript: URLs, or to file: URLs when the extension does not have file access." tabs.connect() no longer also connects to "the opener or opened window of the target tab." A Content-Security-Policy-Report-Only header, which is meant to report violations without enforcing them, had been "incorrectly blocking Safari extension scripts from loading," and that is fixed. alarms.create() now rejects alarm names longer than 1,024 bytes and new alarms once an extension has 500.
The new extension features are developer conveniences. Manifests can now declare "message_serialization": "structured_clone", so messages sent with runtime.sendMessage() "can carry values such as ArrayBuffer and Blob between content scripts and the background page." A windowId property has been added to runtime.MessageSender. And WebKit fixed "excessive memory use in web extensions by registering each event listener only once and delivering runtime and port messages without keeping a copy per listener."
Privacy, identity and sandboxing
Several entries concern what a page can hold on to and what it can prove.
- Cache clearing. "Fixed removing disk cache data not canceling pending cache writes." Before the fix, removing cached data did not stop writes already in progress. The notes do not say which data was affected or how long such writes could take.
- Sandboxed frames. "Fixed events not being dispatched to nodes inside a sandboxed iframe." The notes do not say which events or which sandbox settings were involved.
- Enhanced Security. A fragment-only, same-document navigation "could trigger a page reload when Enhanced Security is enabled." That is fixed.
- Blob workers. A dedicated worker started from a blob URL that was revoked immediately had been getting "a new opaque origin," which blocked it from reading Blob objects or importing other blob URLs.
