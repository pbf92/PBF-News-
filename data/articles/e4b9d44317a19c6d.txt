TITLE: OpenAI uses Codex to investigate ChatGPT slowdowns | ETIH EdTech News
OUTLET: EdTech Innovation Hub

OpenAI says its Performance Factory tracked more than 1,700 investigations in just over three months, with engineers deciding which fixes reach the live service
When ChatGPT image requests kept failing after the service that locates files had recovered, a Codex agent spotted a hole in an earlier diagnosis and reopened the case. The first agent had traced the failing conversations to image download errors. Its reviewer wanted an explanation for why the failures continued.
That second check is part of OpenAI’s Performance Factory, an internal system that uses Codex agents to investigate performance problems, propose code changes and verify that the live service has recovered. OpenAI engineers Okay Zed and Cyrus Forbes described the system on November 19. They say its first workflow tracked more than 1,700 investigations and identified root causes in more than 600 cases in just over three months, averaging about 17 automated investigations a day.
The alert tells engineers something is wrong. Codex looks for when it started
One of the problems OpenAI’s engineers used to investigate by hand was a growing delay before ChatGPT began responding. They would compare service measurements, read logs and inspect code to work out where the time went. Over time, the team built more than 30 performance tools. Codex gave engineers a way to use those tools in investigations, including in parts of the system they knew less well.
Early automation took the investigation as far as a reply in Slack. Engineers still had to find the relevant thread, pick up the diagnosis and check what happened after a fix. The Performance Factory now keeps those findings in a shared task, so an engineer or another agent can pick up the work after a code review or deployment. It also groups alerts that appear to describe the same problem and ranks them by estimated impact.
An alert fires when a measure crosses a threshold. A slowdown can have started hours earlier. Codex looks back to establish when performance began to change and which requests were affected. It also checks whether a particular kind of request got slower or whether the service was handling more requests of a kind that was already slow. Those two patterns send an investigation in different directions.
A second agent challenges the first diagnosis
OpenAI says early agents sometimes settled on the first explanation that fit the evidence they had found. The company added a separate Codex review that tries to disprove the diagnosis. If the first agent blames a software rollout, for example, the reviewer can compare affected requests with similar ones that never received the change.
In a manual review of 100 suggested root causes, OpenAI judged 70% accurate. The remaining 30% needed further refinement or fell short of establishing what caused the problem. The company also tests its agents against past incidents, starting each investigation with the original signal and withholding the incident write-up. It scores findings such as when the slowdown began and how severe it was separately from whether the agent identified the cause.
Engineers decide which fixes reach ChatGPT
Once a diagnosis passes review, Codex can propose a code change. A separate agent checks that the change addresses the cause and looks for possible side effects. An engineer can then edit the proposal, approve it or use the findings to write a different fix.
OpenAI says getting the fix right has proved harder than finding the cause. One example is adding a cache. Keeping a copy of data ready to reuse can speed up a request, but it can also leave users seeing information that is out of date. Engineers who know the service can judge whether that trade-off is acceptable.
After an engineer deploys a change, an agent checks the live measurements against their earlier levels. A full recovery closes the task. If performance improves only partway, the agent opens a new investigation into the remaining slowdown. If it fails to improve, the original investigation resumes.
OpenAI wants to catch slowdowns before an alert fires
The current workflow begins with an alert. OpenAI is working on ways for agents to spot smaller performance changes across software releases, including increases in the processing power needed to handle a request. A change too small to trigger an alert could still give the team a reason to investigate.
OpenAI is also working on tests that would let agents measure proposed fixes and revise them before sending them to an engineer. It is exploring whether some low-risk changes could eventually reach the live service without individual human approval.
