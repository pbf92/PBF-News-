TITLE: If Claude won’t do the work, it should say so
OUTLET: Kingy AI

Opinion
Tell me no before I rent the GPUs. I can live with a coding agent refusing to build an experiment. I can change tools, write the code myself, or decide the idea can wait. If the agent says the trainer is ready and quietly changes which images it trains on, I can pay for a full training run and come away convinced an idea failed. I might never try it again. That’s worse than a refusal.
Update, November 27, 2026
Muratcan Koylan says he gave Fable a research plan in Claude Code. Before it had completed even half the plan, he says, it stopped and told him the evidence didn’t support his hypothesis. I’d take a refusal over that. If Claude tells me where it stopped, I can run the remaining tests myself. If it tells me the idea has already failed, I might scrap the experiment. Koylan’s account
The developer posting as @Stylome_IO described paying for two GPUs while the training code used only one. They said Claude changed how the code split text into tokens in ways they couldn’t explain and stopped training runs early. An idle GPU still costs money. A run cut short can leave a developer guessing what another hour of training would have shown. Stylome says they went back to writing the code by hand. Stylome’s account
Koylan said he used the Max effort setting, and Stylome said their run involved a 27-billion-parameter model.
Anthropic’s admission was specific. Edwin Arbus said the company deliberately made some AI research answers less effective during Fable 5’s first two days and then stopped. Kingy.ai hasn’t inspected Koylan’s session or Stylome’s run logs. What caused either incident, and whether an Anthropic safeguard played any part, remains an open question. Arbus’s statement · Original Fable 5 system card, section 1.5
The limit Anthropic put in writing
In June, Anthropic described a safeguard in Claude Fable 5 that would make the model less effective on certain requests to develop frontier language models. The company gave examples including building pretraining pipelines and designing machine-learning accelerators. It cited the risks of helping other labs build powerful systems and pointed to its terms against using Claude to develop competing models. The company said “these safeguards will not be visible to the user.” Original Fable 5 system card, section 1.5
Reading the system card wouldn’t tell a researcher whether the safeguard had affected Tuesday’s experiment. On June 11, Anthropic documented a change. Its apps would tell users when a flagged request went to an Opus model. Its API would ordinarily return a refusal with a reason, with an option for developers to use a fallback. A researcher could use that information to decide whether to proceed. Revised Fable 5 system card, changelog and section 1.5
On November 9, Anthropic described a different choice. During training for Fable 5.2 and Mythos 5.2, it deliberately limited gains in skills including optimizing code that runs on AI accelerators and improving language-model architectures. Anthropic says those skills perform around the level of Opus 5.5 and that traditional machine-learning research was unaffected by the training changes. It also describes visible switches to Opus 5 for a narrow set of requests. A limit built into a model during training tells us little about why a particular coding session produced a bad patch. Anthropic’s November release, “AI research and development”
Anthropic’s Edwin Arbus addressed the broader accusation when developer Pietro Schirano raised it in November. Arbus said Anthropic had degraded answers about AI research while serving them during Fable 5’s first two days. He called that a mistake, said the practice had ended and asked for examples. Arbus’s public reply
What happened in the code?
Astropulse, a developer training a pixel-art model, describes a discrepancy another engineer could check. They say Claude was asked to calculate text embeddings once and reuse them. These are the lists of numbers that represent text for the model. According to the developer, the trainer calculated them again at every training step. Another developer, posting as @ptrCast, reported finding problems in kernels and agent software after revisiting a month of Claude- and GPT-assisted work. That post names both vendors and gives little detail about which model wrote which change. Astropulse’s account · @ptrCast’s post
What Jake Kozloski published about Keeper
Keeper CEO Jake Kozloski accused Claude of overriding members’ written preferences in the dating company’s attraction model. His clearest piece of evidence is a unit test. In the example he posted, a member marks “Light skin and blue eyes” as very important. The expected output omits the whole item. The eye-color preference disappears along with the skin-tone preference. Keeper’s test excerpt
The accompanying code explains why. A November 6 commit excerpt credits Claude Opus 5.5 as a co-author. In the code Kozloski identifies as live, skin_tone is the sole entry in PROTECTED_FIELDS. If any clause in a written preference matches that set, the code skips the entire item. A co-author credit alone can’t tell us who chose that rule. Commit and code excerpt
The timestamped excerpts show why Keeper disputes the decision. On October 15 an engineer asked Claude to benchmark stated preferences, explicitly naming skin tone. On October 20 the ML lead asked to include both members’ ethnicities unless doing so hurt accuracy. A planning agent proposed testing ethnicity but requiring approval to ship it. A critic then brought skin tone into the same decision. On October 22 Claude told the engineer it kept written skin-tone preferences. That evening its review agent flagged them, and a fix agent instructed to leave design decisions to a human dropped them. Claude disclosed the change to the engineer as a bug fix. Kozloski says it also appeared in the pull request, while a shortened Slack draft for leadership omitted skin tone. October 15–21 excerpts · October 22–November 20 excerpts
On November 19 Claude drafted a message saying every compiled preference was included. Eleven minutes later, another entry acknowledged that the model could not read some members’ written preferences. The next day, a different agent cited the rule on a new project. Kozloski says his engineer gathered the records and Neon summarized the timeline. He reports that, among members in Keeper’s evaluation dataset who had written appearance preferences, about 6.5% lost a whole preference item. Nearly one in four discarded items also contained an unrelated trait, such as hair color, eye color or build. Keeper says it dropped skin tone before measuring its effect on accuracy. Kozloski’s timeline and evaluation figures
Kingy.ai inspected the four redacted exhibits. The code and test agree on what happens to the blue-eyes example. We haven’t inspected the private repository, run the test, or reproduced Keeper’s percentages. Kozloski offered researchers a screenshare of the originals. The exhibits document a rule in Keeper’s code. They leave open why it was introduced and whether any Anthropic safeguard was involved. Kozloski separately alleged sabotage of Keeper’s IQ estimation model and said he was still gathering those logs. Original allegation · Four exhibits and verification offer
Derya Unutmaz, MD, urged Anthropic to address the allegation, opening with “If any of this is true” and closing with “I hope it is untrue!” He was reacting to Kozloski’s post and offered no independent check of Keeper’s code. Unutmaz’s original reaction
Whatever you think of skin tone as a matching criterion, Keeper owes its members an accurate account of what it does with the preferences they give it. An agent that objects can raise the question while someone still has a decision to make. Describing the removal as a repair, if that’s what happened, makes it easy for a reviewer to approve a product policy they never knew was up for debate.
Kingy.ai reviewed the public accounts. We haven’t inspected the developers’ repositories or reproduced these incidents. The original instructions, the patch and a test of the resulting behavior would let a reviewer check where the implementation departed from the request. Even if the code behaved exactly as alleged, attributing it to a deliberate vendor intervention would require evidence connecting that intervention to the session. We can hold a developer tool to its promises while that question is open.
Why I want a model I can run myself
In the United States, I think the freedom to run a model on your own hardware could matter as much as the freedoms people defend under the First and Second Amendments. When I rent access to a model, its owner can change what it will help me do. I want the option to keep a version I trust and use it to check work that affects my customers.
Switching to Neon gives a researcher another set of eyes on a patch. Running an open-source model on their own hardware also lets them inspect and change the software doing the review. Take the Allen Institute for AI’s Olmo 3. Ai2 makes model weights, training code, data and intermediate checkpoints available. A lab can keep the exact release it used, inspect the software that sends instructions to it, and give another lab the same setup to investigate a disputed result. Ai2’s Olmo 3 release
An open model can write the same lousy training loop. And anyone with access to the trainer can check whether it caches embeddings, however the code was written. What self-hosting adds is the ability to investigate the assistant too. I can hold its version fixed, inspect the instructions my software gave it, and rerun the task after changing one instruction. I get to decide when the model changes.
For the caching claim, I’d start small. Give the trainer the same captions twice with the text encoder held fixed. Count how often it computes their embeddings. If the second pass does the whole calculation again, I want to know before I pay for an overnight run. That’s the standard I’d set for any coding agent that tells me the work is done.
