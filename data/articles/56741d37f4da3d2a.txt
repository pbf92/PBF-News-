TITLE: Google's change to Chrome's AI agent feature breaks early testers' code
OUTLET: PPC Land

André Cipriani Bandarra, who leads developer relations for Chrome's AI features according to a LinkedIn profile, told developers building on WebMCP on November 23 to expect "significant changes" in "the next few weeks". WebMCP is the proposed web standard, put forward by Google's Chrome team in February, that lets a website hand an AI agent a list of actions it can take directly - search the catalogue, filter the results, book the table - rather than leaving the agent to read the screen and click buttons like a person. The first change is already in Chrome 160, and it stops some existing code from working.
The post, published on Bandarra's own LinkedIn profile rather than as a Chrome announcement, frames the disruption as the price of stability. "While these will be breaking changes - which can always be frustrating - the great news is that they will allow us to ship a stabilized subset of the API in early 2027," Bandarra wrote. The change the post points to is pull request #348 in the public GitHub repository where the WebMCP specification is written. Its author, Dominic Farolino, opened it on October 15, and GitHub records it as merged into the specification on or around November 19, four days before the post.
In Short
Google's Chrome team is changing how WebMCP, its system for letting websites offer ready-made actions to AI agents, hands those actions over, and the first change in Chrome 160 breaks some code written during the test period. It matters to the companies already building agent-ready checkouts, search filters and booking forms on top of it, and to the tool makers whose software reads those actions. More changes are due within weeks, and a Chrome developer relations lead says a smaller, stable version is planned for early 2027.
What changed in Chrome 160
WebMCP has been available to the public through an origin trial since Chrome 149. That is a time-limited test in which a site registers with Google, receives a token, and can switch on an unfinished browser feature for its real visitors. Bandarra's post says many developers testing WebMCP "might not be familiar with how Origin Trials work".
Bandarra describes the purpose in one sentence: "During an Origin Trial, the goal is simple: give developers early access, gather feedback (from developers, browser vendors, security experts, and beyond), and iterate so the API is stable, secure, and fit for purpose before final launch."
The change itself is narrow, but it sits at the centre of the system. A website using WebMCP registers its tools with the browser. Other software - a browser extension, an agent built into the browser, or a testing tool - then asks the browser which tools a page offers. The call that answers that question is getTools(). According to the post, "getTools() now returns a new Tool interface instead of a RegisteredTool dictionary (and window is renamed to source), fixing execution race conditions and preparing the API for opaque origins and Workers."
From a bundle of data to a tracked object
In the language of web specifications, a dictionary is a plain bundle of named values. Once handed over, it is a copy, with no link back to where it came from. An interface is different: it is an object the browser creates and keeps track of itself.
That distinction is the whole point of the change. The pull request description puts it this way: "This PR introduces the Tool interface which encapsulates a tool's new UUID. Tools are now keyed and identified by this ID. This replaces the RegisteredTool dictionary with the new Tool interface, fixes a number of possible race conditions (such as https://webmachinelearning.github.io/webmcp/#unregistration-execution-race), and also unblocks us from being able to execute [tools] registered by opaque origin documents (see #349)."
A UUID, or universally unique identifier, is a long random code. Before the change, the discussion on the pull request indicates, a tool was in practice recognised by its name. After it, each registration of a tool carries its own hidden code, and two registrations with the same name are no longer the same tool. One participant in the review, posting as kenchris, noted that "the id isn't exposed", meaning page scripts cannot read the code directly.
The rename is smaller. The property that pointed to the browser window where a tool was registered was called window. It is now called source. The GitHub issue the pull request closes carries the title "Rename Tool#window to Tool#source". Neither the post nor the pull request spells out the reasoning beyond linking the work to "opaque origins and Workers". Workers are scripts that run in the background, separate from any visible page. Documents with an opaque origin, such as some sandboxed frames, are pages the browser treats as having no ordinary web address of their own.
The race the change is meant to stop
A race condition is a bug in which two things happen at nearly the same moment and the result depends on which finishes first. The WebMCP specification names one such case in a section labelled "unregistration-execution-race", linked from the pull request, which, as the label suggests, concerns a tool being withdrawn at about the time something tries to run it.
The clearest account of why this matters for agents came from kenchris, in a comment on October 20: "Binding a Tool to one registration is useful for agents. If an agent approves a tool and calls it later, a Tool for an unregistered tool fails to execute even when the same name is registered again. Before, a page could swap the tool under the same name and the old approval would still apply."
Put plainly: under the old design, a person or agent could approve a tool called, say, "checkout", and the page could later quietly replace it with a different function of the same name. The approval would carry over. Under the new design, the approval is tied to one specific registration. If the page withdraws that tool, a later call fails, even if a new tool with the same name appears.
The same comment raised a follow-on point. "As far as I can tell there is no way to change a registered tool, so a changed description is a new Tool with a new id," kenchris wrote. A browser or agent that wants to ask the user again when an approved tool changes "would need to match the new one to the old one by name". That question is tracked separately as issue #262.
The pull request also flags work it does not do. "Note that the spec still doesn't define a native-agent-initiated tool execution path (equivalent to CDP-initiated tool execution in Chromium, or Gemini-in-Chrome/"actor stack"-initiated tool execution in branded Chrome), but that's coming soon, and the changes here are required to support the correctness / race fixes in those areas too," Farolino wrote. Chromium is the open-source code on which Chrome is built; "branded Chrome" is Google's own browser. CDP refers to the Chrome DevTools Protocol, the control channel used by developer and automation tools. In other words, the specification does not yet describe how an agent built into the browser itself, such as Gemini in Chrome, starts a tool, even though the pull request refers to such a path existing in Google's browser.

The pull request lists the compatibility changes in three points. The table below sets them against the earlier behaviour where the sources describe it.
Each of these has a plain consequence. JSON.stringify turns an object into text, which developers use to log data or send it to a server; it now produces an empty object, written {}. The spread operator copies an object's fields into a new one; it now copies nothing. structuredClone makes a copy that can travel between separate parts of a browser, such as a web page and an extension's background process; it now fails outright. The inputSchema field describes what inputs a tool accepts, and annotations carries extra labels. Code that checked whether those fields were "undefined" now meets "null" instead.
For extension builders, the clone problem is real but not new. "We discover tools from a content script and have to pass them on to a service worker and an extension page before the model calls one, so a tool has to cross a few contexts," kenchris wrote. Farolino replied that this "was broken before this PR too", since window was not serialisable either. "Extensions-specific work or something of the sort will take care of this, right. I don't think it'll propagate to any spec changes here, although we may independently make Tool a [Serializable] object anyways (see the discussion in #236)," Farolino wrote. kenchris agreed: "It's not a regression, I was only asking whether it's meant to be possible."
Inside the review
The GitHub record shows a five-week review. Farolino opened the pull request on October 15. Reviewer markafoltz left a first review on October 17 with the comment "Looks pretty good!" and approved the changes on October 21. On the same day Farolino wrote: "Thanks for the reviews! I'll hold off on landing this for a little bit to give @jakearchibald more time to take a look." A second reviewer, beaufortfrancois, also reviewed the changes.
The final version consists of two commits, titled "Introduce the Tool interface" and "window => source", touching two files. The pull request lists 40 conversation entries and four participants, two checks passed, and the merge is recorded as commit 14b6d53. On November 23 the WebMCP repository listed 128 open issues and 10 open pull requests.
Several items linked from the pull request remain unresolved. They indicate where the next changes may land, although neither the post nor the pull request says which of them belong to the coming "breaking changes".
Issue #384 shows the job is not finished. It records that two events, fired when a tool is activated or cancelled, still identify tools "only by name, not Tool interface" - the very weakness the new interface was meant to remove.
The trial behind the change
Public records outside the post fill in the trial's calendar. According to an "Intent to Extend Experiment" notice posted to Chromium's blink-dev mailing list on September 28, the WebMCP origin trial originally ran from Chrome 149 to Chrome 156 on desktop, Android and WebView, and the extension moves its end to Chrome 162. The stated reason was that trial feedback had suggested improvements to the API, which the team was implementing, and that the extension would provide data on those improvements as well as the rest of the feature.
The same thread shows how widely the trial is used. On October 28, a member of the Chrome WebMCP team asked for an exception to the trial's usage cap. WebMCP registrations had crossed the 0.5% warning threshold and stood at about 0.51% of all Chrome page loads; the request asked to allow up to 2.0%. Three Blink API owners posted approvals on October 28, November 2 and November 4, the thread shows.
Farolino's own message on the thread, dated September 29, set out the direction. According to that message, the imperative version of the API, the one driven by JavaScript code, was far more popular than the declarative version built on annotated HTML forms, and the team was investing more in it. Changes under consideration included feedback from Mozilla to make the API useful beyond AI as a generic function-calling mechanism, a continuation API for tasks that start on one page and finish on another, a tool stability signal telling an agent when to take a snapshot of the page, passing a user's click or tap from an in-page agent to the page that hosts a tool, and size and character limits on tools. The message added that the team hoped to file an intent to ship, the formal request to switch a feature on for everyone, within the extension window.
