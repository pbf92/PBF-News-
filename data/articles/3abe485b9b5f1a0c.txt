TITLE: Google documents 12 existing bots that ignore robots.txt
OUTLET: PPC Land

Google today added 12 user agents to the documentation for its crawling infrastructure, and stressed that none of them is new. The update, logged in the crawling documentation changelog on November 23, 2026 under the heading "Documented additional existing crawlers and user-triggered fetchers," puts names and descriptions to clients that already send requests to websites: a Google Analytics process that delivers conversion postbacks to ad networks, the fetcher behind Gmail's image proxy, the Google Ads page renderer called pageburst, the PageSpeed Insights auditor and eight others.
A thirteenth client changed places. APIs-Google, which delivers webhook push notifications for Google Cloud and Google Workspace APIs, moved from the special-case crawlers list to the user-triggered fetchers list, and its documented user agent string gained a semicolon. Its own page now says it ignores robots.txt rules, a reversal of earlier versions of Google's documentation, which described the file as one of two ways to stop it.
In Short
Google has written down the names of 12 automated clients it already runs, plus a corrected entry for a 13th, so that site operators can identify them in their logs. None of the 13 follows robots.txt rules in the way Googlebot does, so the file generally does not stop them, and one of them, pageburst, renders landing pages for Google Ads quality and safety checks. Anyone matching Google traffic by exact user agent string now has a new set of strings to recognise, and code that matched the old APIs-Google string may need the added semicolon.
What the changelog says
The changelog entry is short and the wording matters, so it is reproduced in full. Under "What," Google wrote: "Updated the crawler and fetcher documentation." It then lists three changes.
The first: "Added the following user agents to the special-case crawlers documentation: Google-analytics-postbacks, Google-Calendar-Importer, GoogleDocs, Google-Edu, pageburst, and PlayStore-Google."
The second: "Added the following user agents to the user-triggered fetchers documentation: AppEngine-Google, Google-Apps-Script, Google-Cloud-Tasks, GoogleImageProxy, Google Web Preview, and Chrome-Lighthouse."
The third: "Moved APIs-Google from special-case crawlers to the user-triggered fetchers documentation, and corrected a typo in its documented user agent string (added the missing semicolon after APIs-Google). If you hardcoded the old value in your code, update the string to avoid potential bugs."
Under "Why," Google gave its reasons: "These crawlers and fetchers are not new; we're documenting existing high-volume clients that are more likely to show up in server logs and that we've received questions about. Moving APIs-Google reflects that its webhook push requests come from the user-triggered fetcher IP ranges and ignore robots.txt rules."
The phrase "high-volume clients" is the closest the entry comes to a measure of scale. Google gave no request counts. Search Engine Roundtable, which reported the change at 2:20 pm on November 23, noted that while the clients are not new, they had not been widely known before.
Every new and moved user agent
The table below lists each user agent covered by today's changelog entry, the category Google now assigns it, and what Google says it does. The robots.txt column quotes Google's wording where the entry carries its own line, and the category rule where it does not.
The strings themselves are what log analysts and firewall rules match against. Google publishes them exactly as they appear in HTTP requests. W.X.Y.Z stands for a Chrome version number, and APPID and SCRIPT_ID are placeholders for project identifiers.
Several of these strings borrow browser identities. GoogleImageProxy presents itself as Firefox 11 on Windows XP-era "Windows NT 5.1," and the mobile pageburst string reports an iPad on iOS 9.1. A rule that looks only for "Googlebot" in the header will catch none of them.
Two lists, two sets of rules
Google sorts its non-Search clients into two groups, and today's update shows how much the line between them depends on network plumbing rather than on what a client does.
The special-case page opens with its definition: "The special-case crawlers are used by specific Google products where there's an agreement between the crawled site and the product about the crawl process. For example, AdsBot ignores the global robots.txt user agent () with the ad publisher's permission." It continues: "The special-case crawlers may ignore robots.txt rules and so they operate from a different IP range than the common crawlers. The IP ranges are published in the special-crawlers.json object. The special-case crawlers' reverse DNS mask matches rate-limited-proxy----*.google.com."
The user-triggered page sets out a different premise: "User-triggered fetchers are initiated by users to perform a fetching function within a Google product. For example, Google Site Verifier acts on a user's request, or a site hosted on Google Cloud (GCP) has a feature that allows the site's users to retrieve an external RSS feed. Because the fetch was requested by a user, these fetchers generally ignore robots.txt rules."
Its address details are more complex. "The IP ranges the user-triggered fetchers use are published in the user-triggered-fetchers.json, user-triggered-fetchers-google.json, and user-triggered-agents.json objects. The user-triggered fetchers' reverse DNS mask, depending on whether the fetcher is Google or user owned, matches ---.gae.googleusercontent.com or google-proxy----.google.com respectively."
Both pages carry the same disclaimer: "The list is not exhaustive, it only covers the requestors that are more likely to show up in log files and that we've received questions about." Both also carry a caution: "The user agent string can be spoofed."
The definitions do not map neatly onto the new entries. GoogleDocs, which fetches "user-specified web URLs" for spreadsheet functions such as IMPORTHTML, sits on the special-case list, even though a user types the URL. Google-Calendar-Importer refreshes feeds that users subscribed to. Neither involves an agreement with the site being fetched in any obvious sense. Google's stated reason for moving APIs-Google, meanwhile, rests on which IP ranges its requests come from. In PPC Land's reading, the two lists track infrastructure as much as purpose, which is why the IP files and reverse DNS masks matter more for identification than the category labels.
What the special-case list looks like now
Before today, the special-case page listed five crawlers: APIs-Google, AdsBot Mobile Web, AdsBot, Google-Safety and Mediapartners-Google. Versions of the page last updated in September 2026 show that set. Four of the five had their own robots.txt token, each with the note "The global user agent (*) is ignored." Only Google-Safety, which handles "abuse-specific crawling, such as malware discovery for publicly posted links on Google properties," ignored robots.txt outright.
The page now lists ten. AdsBot, AdsBot Mobile Web and Mediapartners-Google still carry tokens that a site can address by name. The other seven, Google-Safety plus the six added today, each carry the line that the user agent "ignores robots.txt rules." By PPC Land's count, the share of special-case crawlers that can be addressed in robots.txt fell from four in five to three in ten. The change reflects documentation of clients that already existed, not a change in how those clients behave, according to Google.
The user-triggered list grew from nine entries to 16. Before today it held Chrome Web Store, Feedfetcher, Gemini Notebook, Google-Agent, Google Messages, Google Pinpoint, Google Publisher Center, Google Read Aloud and Google Site Verifier. It now adds APIs-Google and the six new fetchers.
APIs-Google: one semicolon and a different robots.txt answer
The APIs-Google changes are small in characters and larger in effect.
The string first. Earlier versions of the special-case page gave the user agent as APIs-Google (+https://developers.google.com/webmasters/APIs-Google.html), with a space after the name. The user-triggered page now gives APIs-Google; (+https://developers.google.com/webmasters/APIs-Google.html). Google calls the old form "a typo" and says the corrected one is "the missing semicolon after APIs-Google." The link inside the string still points to a /webmasters/ address on developers.google.com, a path from before Google moved its crawling documentation to its own site.
The correction runs the opposite way to one Google made earlier this year. On July 14, 2026, the changelog recorded that "The user agent string for Google-InspectionTool mistakenly included a semicolon, which didn't match the actual user agent string in production." Google removed that semicolon. For APIs-Google, it has added one. In both cases the documentation, not the client, was out of line with production traffic, according to Google.
Then robots.txt. On the old special-case page, APIs-Google had a robots.txt token of its own, the note "The global user agent (*) is ignored," and an example group addressed to APIs-Google, mirroring the AdsBot entries. The standalone APIs-Google page, in versions last updated on November 26, 2025 and still served in German, Portuguese and Spanish, listed robots.txt as the second of two ways to stop the notifications. Those versions named APIs-Google as the user agent to specify in the file and said it does not follow rules written for Googlebot.
The English page, updated today, says something else. Under the heading "Prevent APIs-Google from calling your site," it reads: "Because APIs-Google delivers user-configured webhook notifications, it ignores robots.txt rules." The changelog uses the present tense, saying the move "reflects" that the push requests "ignore robots.txt rules." It does not say whether APIs-Google ever honoured rules addressed to it, or whether the documentation was wrong for as long as it said so.
How the APIs-Google page describes stopping and verifying requests
According to Google's updated page, a site that wants APIs-Google requests to stop has two routes, and verification is a separate step. The page describes them as follows.
- Ask whoever set up notifications to disable them. "If you administer a domain that has subdomains or URL subspaces that are owned or administered separately, one of the subdomain owners may have set up an application that uses push notifications," according to the page.
- Report unexpected push requests. Google states that "Some services, such as Cloud Pub/Sub push subscriptions, don't require domain ownership verification when configuring a push endpoint." Requests not configured by the receiving organization go through the "Report suspected abuse on Google Cloud" form.
- Verify the caller. The page says to search logs for IP addresses identifying as APIs-Google, where "a reverse DNS lookup shows the google.com or gae.googleusercontent.com domain."
The page also records delivery behaviour. Each notification is an HTTPS POST. Failed requests are retried "based on an exponential backoff schedule - up to a maximum of several days," and traffic "can be consistent in some scenarios, but in other scenarios the traffic can be sporadic or spiky." Delivery requires a valid SSL certificate, and Google lists self-signed certificates, certificates signed by an untrusted source and revoked certificates as invalid. Responses are expected "within seconds."
Two of the new fetchers come with similar reporting instructions. For App Engine, abuse reports go through the same Google Cloud form and should include "the appid value (https://APPID.appspot.com, omitting any s~ prefix), source IP address, and timestamp." For Apps Script, reports should include "the full User-Agent string (with id: SCRIPT_ID), source IP address, and timestamp."
